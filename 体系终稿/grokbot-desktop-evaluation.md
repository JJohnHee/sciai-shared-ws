# Grok Bot Desktop 对 SCAI 蜂王体系的评估（2026-11-25）

## 总体结论

> "SCAI 已有分层蜂群原型的合理形态，但'6 节点闭环跑通'还不能证明'77 节点生产可用'。"

Grok Bot 特别注明："以下是基于你描述的设计评分，不是代码或运行验收；风险项分数越高，表示风险控制越完善。"

## 六维度评价

### 1. 架构合理性
OS核心、项目主脑、执行层分工合理，但必须明确**调度权、状态所有权和 hub 故障恢复机制**，避免多层重复规划。

### 2. 联通体系
Git适合版本和交付物同步，但**不能替代任务队列、心跳及运行状态**，6节点之外的联通与故障恢复尚待证明。

### 3. 模型路由
强主脑配多模型池具备弹性，但**319个模型不等于319种可靠能力**，模型真实身份、工具调用质量、限流与回退需要逐项验证。

### 4. 调度蜂群
22个Bot的Pipeline闭环是积极信号，但生产调度还要证明**任务租约、幂等重试、背压、取消传播和验收独立性**。

### 5. 与官方ClawsGO对比
未提供可核实的官方版本、功能基线和同题实测，因此**不能负责任地判断领先或落后**。

### 6. 风险盲区控制
当前描述尚未覆盖**跨项目权限、采集内容提示注入、密钥隔离、供应商数据流向及失控费用上限**——这代表证据缺口而非断言没有防护。

## Top 5 行动建议

1. **定义"闭环通过"标准**：每个任务保留输入、调度、执行、独立验收、产物与成本记录，以**真实交付成功率**而非Bot数量衡量能力。

2. **补齐调度可靠性**：Git保留代码和产物，运行任务使用**持久队列**，落实租约、幂等、重试上限、死信和全链取消。

3. **精选模型而非堆量**：从319个候选中选**少量通过同题测试的主用与备用模型**，按任务质量、延迟、成本和数据敏感度路由。

4. **先测故障恢复再扩容**：在现有6节点测试**hub重启、节点掉线、模型限流和重复回执**，证明不丢任务、不重复产生业务副作用后再扩容。

5. **安全基线可测后对标**：项目隔离、最小权限、采集数据不可信、密钥与预算控制必须可测，再用**同一任务集与已核实版本的ClawsGO**比较成功率、人工介入和单次有效交付成本。
