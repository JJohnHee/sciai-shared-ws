## 2. Top 3 立即推进的构建项

排序依据：**卡住最多下游 × 修复成本最低 × 不需要用户新批资源**。

### B1（P0）交付回环闭环：产物回收 + 自动汇总裁决 + 幂等派发（S6 + G3 + S8）
- 为什么第一：所有部门（含新部门）production 都会掉进同一个坑——干完了收不回来、多份产物没人裁、resume 两次出两版。不修它，部署 5 个新部门只会把「滞留产物的量」乘 5。
- 现有半成品：`thesis-swarm` 已验证 dispatch read-back 通道可代用（STATE 会话三），`s8-acceptance-test.sh` + `s8-test-tasks.db` 已有测试夹具。

### B2（P1）新部门编制：分批「入池」，先把 1 个部门跑通全链再复制
- 为什么第二：l1/L4/L5/K3/nvidatwo 当前是三种状态（空机 / 未纳管 / 缺端点），一次性铺开必然大批半成品。用 `departments/DEPARTMENT-TEMPLATE.md` + `bots/dept-research-*/` 作为配方，**先拿 l1 竞调部做样板**（可 SSH、与阶段2 已有尽调工单业务对齐），L5 写书部第二个（与阶段2「书稿 l4」待拍板业务对齐）。
- L4/L5/K3 在主机名进不了 ssh config 之前，**不派部署，先投 INBOX 问用户这三台是真机还是待采购**——这是必须用户裁决的前置。

### B3（P1）编制一致性 + 客户端可执行清单收口（glm-5.2 清理 / 技能注册表 / 28 桥能力落盘）
- 为什么第三：都是低风险、纯文档/注册表层面的「清账」，但它决定 B2 复制出来的新部门不会继承旧配置错误，也决定客户端这条线能不能被拆成故事来推进。
- 具体：① 舰队 glm-5.2→5.3 全量改（E7 四处）② hub 技能注册表加 epic-breakdown-advisor、口径改 13 ③ 依 `CLIENT-REPLICA-GAPS.md` 缺失（E9）**重建** 28 项清单，用 epic-breakdown-advisor 拆成可排的故事。

### 关于 farm 通道（独立跟进，不进 Top 3）
farm 0 台（E2）影响的是「出站被墙」场景的采集产能，但当前 30 台在线池 + 天翼云 evide 不足，B1/B2/B3 不依赖它。**列为 P2 跟进项**：在 STATE 里保持记录，下一次 hub:8778 devices-meta 快照时确认真断还是仅 register 缺失；farm 有独立复通路径（R59-R61 结论），不需要占用 Top 3 的工程带宽。
